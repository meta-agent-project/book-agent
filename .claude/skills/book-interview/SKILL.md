# book-interview

## 역할
현재 대화의 정보를 먼저 수집해 부족한 설계 조건만 인터뷰한다. 산출물은 다음 단계 `book-syllabus`가 그대로 읽을 수 있는 **브리프**다. 아래 7개 항목만 묻는다. 총 시간, 강의 형식(오프라인/VOD), 목차 용도는 묻지 않는다. 인터뷰 중에는 목차 초안을 만들지 않는다.

## 진행
1. 첫 요청과 대화에서 7개 항목의 이미 알려진 답을 추출하고 짧게 확인한다.
2. 미확인 항목을 아래 순서로 **한 메시지에 하나씩** 묻는다. 이미 답한 내용은 이어받는다.

| 순서 | 항목 | 질문과 판단 기준 |
|---|---|---|
| 1 | 학습목표 | “수료 후 무엇을 할 수 있어야 하나요?” 동작·산출물 중심으로 구체화 |
| 2 | 선수지식 | 수강생이 이미 아는 것과 처음 배우는 것 |
| 3 | 후속과정 | 있음/없음, 있으면 과정명 |
| 4 | 강의방법 | 이론 중심(개념→코드 예시) / 실습 중심(짧은 개념→실습) / 프로젝트형(프로젝트를 따라 만들며 개념 학습) |
| 5 | 반드시 넣을 주제 | 후보에서 번호 선택, 직접 추가 가능 |
| 6 | 빼도 되는 주제 | 5번의 후보와 같은 번호 유지, 선택 완료 항목 제외 |
| 7 | 실행 환경 | 에디터·실행 방법·버전, 코드 유형별 실행 방식까지 확인 |

3. 5번 질문 전에 학습목표와 선수지식에 맞는 **15~25개** 후보를 4~5개 묶음으로 제시한다. 번호·주제명·한 줄 설명·추천 여부를 함께 제시한다. 선수지식에 해당하거나 범위 밖의 흔한 주제도 선택지에 포함한다. 6번에 같은 번호를 사용한다. 브리프에는 선택 번호 대신 주제명을 기록한다. 후보 목록은 AskUserQuestion이 아니라 일반 메시지로 보여 주고 번호로 답받는다(AskUserQuestion은 선택지가 4개로 제한된다). 후속과정과 강의방법은 AskUserQuestion 객관식으로 물어도 된다.
4. “모르겠다/알아서”는 **미정**으로 기록하고 다음 항목으로 이동한다.
5. 7개 항목을 모으면 브리프를 보여 주고 수정 의견을 받는다. 확인 후 저장 승인을 받으면 `.book/interview/{YYYY-MM-DD}-{주제-slug}.md`에 저장한다.

## 브리프 형식

```markdown
# 강의 설계 인터뷰 브리프: {강의 주제}
- 날짜: {YYYY-MM-DD}

## 인터뷰 결과
| 항목 | 내용 |
|---|---|
| 학습목표 | {행동 중심 목표} |
| 선수지식 | {아는 것/처음 배우는 것} |
| 후속과정 | {있음: 과정명/없음} |
| 강의방법 | {이론 중심/실습 중심/프로젝트형} |
| 반드시 넣을 주제 | {주제명/없음} |
| 빼도 되는 주제 | {주제명/없음} |
| 실행 환경 | {에디터, 실행 방법, 버전, 코드 유형별 실행 방식} |

## 미정 항목
{항목과 다음 단계에서 필요한 가정/없음}

## 고정 조건
- 목차는 장 > 세부목차 두 단계(파트 없음).
- 이론·실습 중심: 모든 일반 장에 연습문제, 주제 단위가 끝날 때 독립 미니프로젝트 장, 마지막에 기존 미니프로젝트를 조립하는 종합 프로젝트 장.
- 프로젝트형: 각 장에서 프로젝트를 이어 구현하며 개념을 설명. 독립 프로젝트 장 대신 장별 시작 체크포인트 코드 제공. 장 끝에 연습문제.
- 연습문제 형식·프로젝트 소재는 계획서 초안 검토 때 조정.

## 참고 메모
{수강생 특징, 선호 예시 등/없으면 생략}
```

## 완료 조건
인터뷰가 독립 요청이면 브리프 확인 후 종료한다. `book-syllabus`가 호출해서 시작한 인터뷰라면 브리프 확인 후 원래 계획서 작성 흐름으로 복귀한다.
