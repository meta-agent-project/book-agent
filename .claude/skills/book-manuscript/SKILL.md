# book-manuscript

## 역할과 입력
기본 단위는 한 장이며, 사용자가 여러 장·전체를 요청하면 그 범위를 연속해서 작성한다. 각 장은 수강생이 앞 장에서 배운 지식만으로 따라갈 수 있게 만든다.

먼저 [과정별 집필·개편 흐름](references/authoring-workflow.md)을 읽고 원고폴더와 설계폴더를 선택한다. 이 문서의 경로는 선택한 과정으로 바꿔 적용한다. 저장된 과정별 합의와 프로젝트 형식이 공통 장 형식보다 우선한다.

| 층 | 읽을 자료 | 목적 |
|---|---|---|
| 공통 기준 | `references/style-guide.md`, `references/title-style.md`, `references/few-shot.md` | 문체·블록·코드·검수 기준 및 형식 예시 |
| 과정 | `{설계폴더}/interview/`, `{설계폴더}/syllabus/`, `{설계폴더}/manuscript/course-setup.md` | 목표·대상·세부목차·환경·도메인 |
| 진행 | `{설계폴더}/manuscript/ledger.md` | 앞 장의 개념·API·명칭·미룬 내용 |

경로는 프로젝트 루트 기준이다. `references/`는 이 스킬 폴더 내부를 뜻한다. 집필 전에 `references/style-guide.md`와 `references/few-shot.md`의 실제 내용을 모두 읽고 시각자료 기준과 완성 예시도 확인한다. few-shot에서는 **형식만** 참고하며 실제 주제와 실행 환경은 과정 설정을 따른다.

## 절차
과정 설정에 별도의 **코드 few-shot** 경로가 있으면 그 문서도 읽는다. 공통 few-shot은 장 구성·문체의 예시이고 과정별 코드 few-shot은 예제의 구성·복잡도 기준이다. 채택한 규칙은 과정 설정을 따른다. 특정 과정의 코드 스타일을 다른 교재에 자동 적용하지 않는다. 사용자가 승인한 스타일을 여러 장에 일괄 적용하도록 요청했으면 그 범위에서 진행하며 장마다 같은 질문·확정을 반복하지 않는다.

1. **계획서 확인:** `{설계폴더}/syllabus/`에서 대상을 선택하고 계획서의 브리프를 읽는다. 계획서가 없으면 `book-syllabus` 작성 여부를 확인한다.
2. **과정 설정:** `course-setup.md`와 연결된 코드 few-shot을 읽는다. 최초 작성 시 아래 항목을 브리프·계획서·사용자가 준 few-shot으로 채워 저장한다. 이미 합의한 기준은 다시 확인받지 않는다. 실행 환경 등 집필에 필요한 정보가 불명확할 때만 질문한다.
3. **장 선택:** 지정한 장을 우선한다. 미지정이면 ledger의 다음 미작성 장을 제안한다. 이전 장 없이 진행하면 선수 지식과 코드 연속성에 대한 제한을 밝히고 진행 여부를 확인한다.
4. **장별 기준:** 계획서와 장부에 이미 정한 비중·비유·예시가 있으면 그대로 적용한다. 최초 설계에서 집필에 필요한 기준이 부족할 때만 장별 질문을 모아 묻고 답을 장부에 기록한다. ‘없음/알아서’면 계획서 비중을 따른다.
5. **연속성 확인:** ledger를 읽는다. 없으면 첫 장이므로 아래 필수 필드로 새로 만든다. ledger를 읽고 앞 장에 나온 용어·문법·API·파일명·함수명을 이어 쓴다. 새 개념은 해당 장에서 이해할 만큼 설명하고, 이전에 미뤄 둔 주제 중 이번 장 해당 사항을 다룬다.
6. **집필:** 계획서의 장 제목·세부목차 번호와 이름을 유지한다. 모든 장의 도입에는 `**학습목표**`를 쓴다. 실행 환경 설치·설정·실행 방식은 01장의 ‘실행 환경 준비’ 세부항목에 모으고, 장별 도입과 따라하기에 환경 블록을 반복하지 않는다. 장 유형과 강의방법에 맞춰 `style-guide.md`의 구조·코드 형식을 적용한다. **정의·쉬운 설명 → 왜 필요할까 → 특징 → 비교 → 비유 → 그림 → 기본 문법 → 완결 예제·실행 결과 → 따라하기 실습(전체 코드) → 연습문제 → 정답과 해설** 중 해당 소제목에 필요한 요소를 배치한다. 왜 필요할까는 이유가 분명하지 않은 개념에 판단해서 넣고, 특징은 규칙이 있는 개념에 하이픈 목록으로, 다른 개념과 견주는 내용은 비교표로, 비유와 그림은 꼭 필요할 때만 둔다(`style-guide.md` 4장 "왜 필요할까" "특징" "비교" "비유" "그림"). 실제 소제목 구성은 계획서·스타일 가이드를 우선한다. 아래 ‘시각자료 구성’에 따라 설명할 흐름·분기·관계·구조·상태 변화·비교를 확인하고, 이해를 돕는 시각자료를 해당 설명 가까이에 실제로 작성한다. 계획서에 `- 예제: 외부 예제`로 적힌 장은 `style-guide.md`의 외부 예제 장 구성만 쓰고 코드·해설·시각자료·검증을 생략한다. 뒤 장은 외부 예제 장의 코드를 가져다 쓰지 않는다. 종합 프로젝트가 그 코드를 조립해야 하면 사용자에게 묻는다.
7. **검증:** 기본 문법의 형태와 실제 실행 예제를 구분한다. 완결 예제·따라하기·바꿔 보기·정답을 세션 임시 폴더(scratchpad)에 원고의 파일명 그대로 저장해 실행하고 서술한 결과와 비교한다. 코드 조각은 바탕 예제에 적용한 뒤 확인한다. `.js`는 Node.js, `.html`은 가능하면 브라우저로 검증한다. 콘솔 결과는 실제 실행 로그로 적고, HTML 결과 페이지는 Playwright로 캡처해 `{원고폴더}/images/{NN}/`에 저장한다(`style-guide.md` 6장 "실행 결과 화면"). 개념 그림은 `scripts/capture-figure.mjs`로 PNG를 만들고 열어서 확인한다. 브라우저 실행이 어려우면 직접 검토하고 미실행 항목을 명시한다. 에러 학습 항목은 에러 이름·메시지·위치·처리 결과까지 확인한다.
8. **초안 저장·검토:** 초안은 처음부터 `{원고폴더}/{NN}장-{장 제목}.md`에 저장한다. 사용자가 그 파일을 직접 열어 검토하므로 scratchpad에 두지 않는다. NN은 두 자리, 파일명 공백은 `-`, 대괄호는 제거한다. `{원고폴더}/`은 장 원고 전용이다. 결과 캡처 이미지는 `{원고폴더}/images/{NN}/`에 둔다. ledger에 해당 장을 `상태: 초안`으로 기록한다. style-guide.md의 시각자료 기준, 읽기 쉬움(R-1~R-9), MD 가독성(MD-1~MD-5), 검수 체크리스트를 확인한다. 복잡한 흐름·분기·관계를 글로만 설명해 필요한 시각자료가 빠졌는지도 확인하고 보완한다. Mermaid의 문법과 화살표·조건·용어가 본문 및 예제 코드와 일치하는지 검증한다. 렌더링 도구가 있으면 실제로 렌더링하고, 없으면 직접 검토한 범위를 밝힌다. `node .claude/skills/book-review/scripts/check-markdown.mjs <원고 경로>`로 형식 검사도 수행한다. 원고 파일 경로와 실행 검증 결과를 알리고, 피드백을 그 파일에 반영한다.
9. **문체 다듬기·보존 검사·최종 검수:** 코드·내용 검증을 마친 초안을 백업하고 `references/title-style.md`와 `book-review`로 본문을 다듬는다. 코드·수치·고유명사·기존 제목·문단·목록·표 구조를 보존하고, 보호 검사를 통과한 뒤 최종 검수한다. 내용 오류는 별도로 기록하며 내용 개편으로 돌아가 처리·실행 검증 후 다시 문체를 다듬는다. 보호 영역이 동일하면 기존 실행 결과·캡처·도표를 유지한다. `references/authoring-workflow.md`에 따라 새 원고는 읽기용 HTML, 기존 원고 개편은 좌우 비교 HTML을 생성·검증하고 브라우저에 직접 연다. 원고 경로와 검증 결과를 보고한다. 사용자 확정 전에는 초안으로 유지하며, 확정 지시가 있으면 장부를 갱신한다. 여러 장을 요청받았으면 같은 확정 질문을 반복하지 않고 요청 범위를 완료한다.

## 목차가 바뀔 때
원고는 계획서를 따르므로, 집필 중에 목차가 바뀌면 원고보다 계획서를 먼저 고친다. 지금 쓰는 장이 아닌 장의 변경도 같다.
- 사용자가 장·세부항목·연습문제를 더하거나 빼거나 옮기거나 이름을 바꾸면 `{설계폴더}/syllabus/`의 계획서를 고친다. 세부목차와 한 줄 설명, 바뀐 이유가 있으면 `가정한 것`도 고친다. 번호가 밀리면 같은 장의 뒤 번호를 모두 고친다.
- 세부항목을 새로 넣으면 한 줄 설명 아래에 `이유:` 줄로 배우는 까닭을 쓴다. 원고의 "왜 필요할까"는 이 이유를 따른다.
- 고친 뒤 영향을 찾는다: 이미 쓴 원고(`{원고폴더}/`)에서 바뀐 번호·제목을 가리키는 곳이나 바뀐 내용과 어긋나는 코드, ledger의 장별 기록과 `앞으로 미룬 설명`, 계획서 안에서 다른 세부항목을 가리키는 설명.
- 확정된 장의 원고를 고쳐야 하면 고치기 전에 사용자에게 알린다. 초안인 장은 바로 고친다.
- ledger의 `앞으로 미룬 설명`에 바뀐 내용과 날짜를 남기고, 바뀐 장이 이미 있으면 그 장 기록에 `구성 변경` 줄을 단다.
- 고친 파일과 영향을 찾은 결과(어긋난 곳이 없으면 없다고)를 보고한다.

## 시각자료 구성
- 세부항목마다 시각화할 설명이 있는지 검토한다. 실행 순서, 조건 분기, 요소 간 관계, 데이터 구조, 상태 변화, 값 비교를 글로 따라가기 어려운 곳에는 시각자료를 포함한다.
- 흐름·순서·분기·관계·ER은 Mermaid, 메모리 칸·배열 칸·화면 배치는 텍스트 도식, 값·특성 비교는 표로 표현한다. Mermaid는 표현 목적에 맞는 종류를 고르고 핵심 분기·반복·예외를 보존한다. 실제 상태 전이가 학습목표면 상태도를 허용한다. 흐름은 먼저 한 장으로 쓰고 book-mermaid로 재 본 뒤, 한눈에 읽히지 않으면 완료·실패처럼 끝나는 곳 기준의 시나리오 그림으로 나눈다. 돌아가는 전이는 해당 시나리오 그림에 유지한다. 상세 선택 기준은 book-mermaid의 ‘Mermaid 다이어그램 작성 규칙’, 형식은 `style-guide.md` 6장을 따른다.
- 원고의 `**시각자료 — 그림 이름**` 아래 실제 Mermaid 코드 블록 또는 텍스트 도식을 작성하고, 그림 아래에 읽어야 할 핵심을 짧게 설명한다. Mermaid는 book-mermaid로 렌더링해 검증하며 책 원고에도 Mermaid 코드 블록을 그대로 둔다. Mermaid로 그릴 도식은 PNG/SVG 이미지 링크나 생성 이미지 자리로 대체하지 않는다.
- 비유나 쉬운 예시 장면이 있는 개념에는 기본 문법 바로 위에 그림을 하나 둘 수 있다. 사물이 나오는 비유 장면은 생성 이미지 자리로, 상자와 화살표 같은 개념 구조는 직접 그린 개념 그림으로 둔다. 두 종류 모두 `assets/style-ref/`의 선 그림 스타일(흰 배경, 검정 선, 기본 흑백)을 따르고, 색은 꼭 필요할 때만 한 가지를 쓴다. 생성 이미지는 글자를 넣지 않고 Codex CLI로 만든다(`scripts/generate-image.mjs`). 상세 형식은 `style-guide.md` 6장 "그림"이다.
- 장마다 그림 개수를 강제하지 않는다. 단순한 문법 설명은 생략할 수 있지만, 시각자료가 필요한 설명을 생략 대상으로 처리하지 않는다.
- few-shot의 변수 선택 흐름도와 할 일 추가 흐름도를 형식 예시로 삼는다. 현재 장에서 아직 배우지 않은 조건이나 기능을 그림에 미리 넣지 않는다.

## course-setup.md 필수 필드
```markdown
# 원고 과정 설정: {주제}
- 원고: {원고폴더}/
- 강의계획서: {경로}
- 코드 few-shot: {과정별 코드 기준 문서 경로/없음}
- 집필·개편 흐름: .claude/skills/book-manuscript/references/authoring-workflow.md
- 검토 HTML: {새 원고 읽기용·개편 좌우 비교 출력 경로}
## 실행 환경
- 에디터: ...
- 실행 방법: {코드 유형별 도구와 명령}
- 버전: ...
- 예제 형태 규칙: {예: 콘솔=단일 .js, DOM=단일 .html}
## 실습 파일 규칙
- {장별 폴더·파일 이름}
## 예제 도메인
- {일반 예제와 프로젝트 소재}
## 코드 컨벤션 예외
- {없음/과정별 예외}
```


## 원고를 만드는 긍정형 기준
- **정상 작동하고 올바른 결과를 보여 주는 코드**를 개념 예제·따라하기·바꿔 보기의 기본값으로 사용한다.
- **오류와 실패 사례는** 장마다 넣는 틀로 쓰지 않는다. 계획서에서 `에러 메시지 읽기`, `예외 처리`, `요청 실패 처리` 등을 배우는 세부항목과, 목적이 에러를 막는 기술(없는 값에 안전하게 접근하는 문법 등)을 설명하는 곳에서 교육목적과 실제 에러 출력을 밝혀 다룬다(`style-guide.md` 4장 "에러를 다루는 범위").
- **따라하기**에는 처음부터 끝까지 실행 가능한 전체 코드를 제공한다. **연습문제**는 수강생이 직접 해결하도록 문제와 정답·해설을 분리한다.
- **기본 문법**은 문법 형태를 보여 주며, **예제**에는 코드와 검증된 실행 결과를 제시한다. **코드 조각**은 적용할 원본 예제와 변경 위치를 명확히 한다.
- 같은 기능군은 **한 실습에서 비교**하고, 코드의 변수·함수·파일명은 장 전체에 걸쳐 일관되게 사용한다.
- 학습자가 찾아보기 쉽도록 제목은 **개념 이름 중심**으로 쓰고 장의 세부목차는 계획서를 그대로 유지한다.
- 설명은 **짧은 문단과 명확한 정의**, 학습 수준에 맞는 구체적 예시로 쓴다. 코드 위치는 줄 번호보다 실제 구문을 인용해 안내한다.
- 본문과 목록의 줄 끝에는 줄바꿈용 역슬래시를 붙이지 않는다. 문장은 한 줄에 하나씩 쓰고, 이어지는 문장은 빈 줄 없이 다음 줄에 쓴다. 빈 줄은 내용이 바뀔 때만 두고, 앞 문장을 이어 설명하는 문장 사이에는 빈 줄을 넣지 않는다.
- 공통 제목·문체는 `title-style.md`, 코드 컨벤션·R/MD 규칙은 `style-guide.md`를 사용한다. 문체 교정에 새 비유·설명·코드 변경을 섞지 않는다.

동일한 피드백이 반복되면 과정 한정 기준은 `course-setup.md`, 여러 강의에 공통인 기준은 `style-guide.md`에 반영할지 확인한다.
